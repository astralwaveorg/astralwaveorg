# OpenClaw Agent 调度能力建设实录：从 8 秒协议到 15 秒阈值

这次把 OpenClaw Agent 的调度能力重新整理了一遍，收获比预期大。记录下来，供以后参考，也供有类似需求的同行少走弯路。

## 背景：为什么突然要重构

起因是我发现一个问题——我给系统派任务的时候，它经常在后台跑着跑着就没下文了。查了一下原因：任务分派出去了，但结果没有回收，也没有闭环。用户（也就是我）不知道任务跑到哪一步了，也不知道最后是成功了还是失败了。

这不对。

调度中枢的核心职责不是"把任务派出去"，而是"让任务有结果"。派出去不算完成，回收验证才算是闭环。

同时还有另一个问题：Agent 在回复里经常把思考过程也写出来。这在某些场景下是可以接受的，但在实际工程使用中，这种输出方式让对话变得混乱，也暴露了内部推理路径。

还有一个更严重的问题：Agent 做出承诺之后，只是口头说"我会注意"，但没有从约束层面解决。下次开新会话，同样的问题还会发生。

这三个问题加在一起，说明系统的调度逻辑和约束规范都需要重新梳理。

## 第一步：重新定义角色边界

一开始系统里有一段提示词是从别的地方复制过来的，里面的角色描述不够准确。Agent 的定位是"执行中枢"，类似于 CEO，而不是前台助手。用户的定位是"最高决策指挥官"。

这个定义很重要。定义不清，调度逻辑就没有根基。

重新梳理后的角色关系如下：

- 执行中枢（我）负责判断、调度、兜底、验证和闭环交付。
- 用户负责目标、授权和关键取舍。
- 调度只是手段，结果闭环才算完成。

在这个框架下，Agent 不能在没把握的情况下承诺结果，也不能把"已派发"当成"已完成"。

## 第二步：调度协议的设计

### 从 8 秒到 15 秒

之前有个"8 秒协议"的想法：任务在 8 秒以内就前台直接回复，超过 8 秒就后台执行。

这个想法的方向是对的，但 8 秒这个数字拍脑袋成分比较大。

经过今天的推演，把阈值调整到了 15 秒。这是一个经验值，核心依据是"是否会让用户感受到等待"。15 秒以内的前台直接执行，原地返回结果；超过 15 秒或者不确定的，立即转后台，出发前告知用户预计时间和回收方式。

这个调整不是小事。阈值设得太短，后台任务会很多，导致管理成本上升；设得太长，用户等待时间会过长，体验差。15 秒是一个相对平衡的折中。

### 调度出发前的告知

光有阈值还不够。后台任务启动之前，必须告知用户三件事：

1. 要做什么
2. 要多久（保守估计）
3. 如何回收

格式大概是这样的：

> 好的，我来解决这个问题。大概需要 3~5 分钟，完成后直接在这里回复你。

不能什么都不说就转后台，那样用户会以为任务卡住了。

### 调度之后的闭环

调度出去的任务必须有兜底链：

1. 检查产出是否存在
2. 检查产出是否可用
3. 可用则验证后采用
4. 不可用则中枢接管
5. 接管仍失败，再向用户说明阻塞点

这里有一个重要的原则：worker 失败不等于任务结束。中枢必须兜底，不能把失败原样转发给用户当成交付。

## 第三步：ACP 配置的规范化

在配置 ACP（Agent Communication Protocol）的时候，踩了一个坑。

系统里 `acp.allowedAgents` 初始只配置了 `["claude"]`，导致其他 ACP agent（例如 codex）会被策略拒绝：

```
ACP agent "codex" is not in the allowlist
```

当时的修复方案是把 `acp.allowedAgents` 设为空数组 `[]`，根据 schema 说明，空数组表示"不再额外限制 allowlist"，而不是"全部禁用"。

但更重要的是学到了一个原则：ACP 参数配置不能靠猜，必须查 schema 和官方文档。OpenClaw 的 gateway 配置直接影响进程行为，配置错了网关会直接挂掉。重要参数必须先查证再写入，不能根据错误信息反推。

这次还顺便把 spawnTimeoutSeconds 从 120 秒调整到了更合理的值。120 秒对于复杂任务来说太短了，容易在任务中途超时。

## 第四步：约束规范的收敛

### 空口承诺问题

这是本次最值得记录的问题之一。

Agent 之前存在一个行为模式：被指出问题后，只是口头说"我会注意"、"我会持续改进"，但不从约束层面解决。结果就是下次开新会话，同样的问题还会发生。

正确的处理方式是：

1. 识别问题根源（哪个文件、哪条规则没有约束住）
2. 说出具体要改什么
3. 立即执行（写入文件或配置）
4. 告知改动内容

如果当前无法执行，必须说明阻塞原因和需要确认什么，而不是用空话敷衍。

### Visible Thinking 的输出约束

Thinking 轨迹属于内部推理记录，只允许出现在工具调用的元数据里。禁止在对话中引用、重述、或暗示内部推理路径。

Visible reply 只允许出现：结论、证据来源、当前执行的动作。

这不只是一个"用户体验"问题，而是一个系统行为的规范性约束。

## 第五步：工具参数的规范化

在测试 subagent 调度的时候，遇到了参数错误的问题。

`sessions_spawn` 的参数在不同 runtime 下有不同约束：

- `runtime="subagent"`：支持 `lightContext: true`，这是 subagent 专属参数
- `runtime="acp"`：不支持 `lightContext`，会直接报错

混用参数会导致 `spawn_failed`，而且错误信息不会直接指向参数名，容易让人走弯路。

这个问题暴露了工具使用规范的重要性。对于 `sessions_spawn` 这类复杂工具，最好是在 TOOLS.md 里明确标注每个参数的适用 runtime，避免混用导致的错误。

## 总结：调度能力的建设不是一次性的

这次重构解决了几个具体问题，但更重要的是建立了一个持续审视和优化的机制。

调度能力建设的核心不在于"一次性配置完美"，而在于：

1. 角色定义清晰，执行边界明确
2. 调度协议有明确的时间阈值和告知规范
3. 约束规范从文件层面落地，而不是口头承诺
4. 工具参数有清晰的 schema 约束

后续如果有新的调度场景暴露了新问题，就继续按这个流程走：先定义问题，再查证规范，再落地修改，再验证闭环。
